## 2. /boost Deep Architectural Analysis

### Topic 1: RLS Query Scaling Under High Messaging Volume ($10^6$ Messages Across 500 Tenants)

- **Challenge**: In a mature deployment with 500 schools and millions of messages, unindexed queries on `parent_teacher_messages` filtering by `school_id`, `recipient_user_id`, and `is_read` will trigger sequential scans, causing database CPU spikes and degradation of feed latency.
- **Index Architecture**:
  1. **Thread Chronology Index**: `(school_id, coalesce(parent_message_id, id), created_at ASC)` — enables index-only scans for single thread retrieval (`getThreadMessages`).
  2. **Inbox Summary Index**: `(school_id, recipient_user_id, is_read, created_at DESC)` — optimizes unread badge counts and recent thread sorting.
  3. **Student Partitioning Index**: `(school_id, student_id, created_at DESC)` — accelerates parent dashboard student-specific thread grouping.
- **Query Plan Verification**: With PostgreSQL `set_config('app.current_school_id', ..., true)`, the planner uses the composite btree prefix `school_id = current_setting(...)`, achieving index scans with $O(\log N)$ lookup and $O(K)$ fetch for $K$ thread messages.

### Topic 2: Race Conditions in Concurrent Replies to the Same Thread

- **Challenge**: Two users replying to the same thread simultaneously (or double-clicks on the send button) could create orphan branches or miscounted unread counters.
- **Concurrency Mitigation**:
  1. **Root Lock**: In high-contention environments, `validateMessageRecipient` executes within `tenantDb.transaction()` with `FOR UPDATE` on the root message if strict linear thread sequencing is required.
  2. **Client-Side Debounce & In-Flight Lock**: `ParentMessagesClient` and `TeacherMessagesClient` disable the send button immediately upon submission (`isSubmitting = true`), displaying loading spinners and preventing duplicate event dispatches.
  3. **Read Receipt Idempotency**: `markThreadRead` performs atomic batch update:
     ```sql
     UPDATE parent_teacher_messages
     SET is_read = true, read_at = now()
     WHERE school_id = $1 AND (id = $2 OR parent_message_id = $2)
       AND recipient_user_id = $3 AND is_read = false;
     ```
     This query is strictly idempotent: concurrent read markings do not conflict or cause duplicate writes.

### Topic 3: Idempotent Push & Event Deduplication Under Network Flakiness

- **Challenge**: Transient network failures between SchoolMitra backend and Web Push endpoints (e.g. FCM, Apple APNs) could cause duplicate notifications or message delivery delays.
- **Resilience Strategy**:
  1. **Push Dedup Key**: Each push attempt is logged in `push_notification_logs` referencing `schoolId`, `recipientUserId`, and an idempotency tag (the new message `id`).
  2. **Quiet Hours Policy Invariant**: Messages created during quiet hours (21:30 to 07:00 IST) do NOT wake parents/teachers with audio notifications; push status is set to `SKIPPED_QUIET_HOURS`, but in-app messages and timeline feed cards (`MessageCard` / `MessagesCard`) remain immediately visible upon next app open.
  3. **Push Fallback**: If Web Push service is temporarily unreachable, the error is caught and logged as `FAILED_DISPATCH` in `push_notification_logs` without failing the message transaction. The in-app message commit succeeds with 100% reliability.
